# Verification

## The rule

A check counts as evidence only if it could fail. Every check here:

1. **Runs the real engines.** It never mocks the thing in doubt: MaBoSS, libRoadRunner and the FV solver all run for
   real.
2. **Has an oracle independent of the code under test:**
   - an analytic solution;
   - another engine's output;
   - the upstream project's own reference output;
   - an exact equivalence against the unmodified upstream model.
3. **Should have a proven-failing negative.** A mutated copy (a wrong expected value, a wrong rate, a wrong network) is
   run and fails on exactly the expectation it should. The negatives are listed below; six checks do not have one
   recorded yet ("—").

## What the checks cover, and what they do not

The checks verify the model's parts: each layer, each coupling and each clock rule. They do not cover the studies'
results. Those are computed by committed scripts from committed run data (Study 0: `run_grid.py`, `analysis.py` and
the `data/` files, {doc}`../design/calibration`), so every number on those pages can be recomputed. Their statistics
are derived in {doc}`../math/statistics`. The documentation's generated tables (the Calzone and Lipniacki tables and
the TransRate race) are regenerated by scripts whose `--check` mode fails when a table is stale.

## How a check runs: exactly as compose-api runs it

`compose/check.sh <group> [<case>]`:

1. Reads `checks/<group>/<case>/case.yaml`, which is compose-api's compliance-case format.
2. Runs the case's document through **compose-api's own `runner.py`**, vendored byte for byte at compose-api 0.7.91
   (`compose/RUNNER_SOURCE`). It runs in `compose/`'s environment, pinned to the commits compose-api's registry pins.
3. Scores the results file with **compose-api's own `compliance.evaluate`**, read from a compose-api checkout
   (`COMPOSE_API_DIR`).

**The harness proves itself.** `checks/harness` holds two of compose-api's own compliance cases, copied unchanged. Both
pass here as they pass live (production runs 9825 and 9828). With one expected value changed, the MaBoSS case fails on
exactly that value.

## Live runs against a local run

`compose/live.py` fetches live compose-api runs with compose-api's own CLI. Each run's archive holds the document as
the service ran it, and that document is run locally through the same runner. The script compares every emitted
value over every row, against the local run and against the other live runs; a value missing on one side, or not
finite on one side only, differs. It writes to `compose/live/<composite>.yaml` the environment each run used, the
machine and simulator packages of the local run, and a verdict per emitted key: identical, within a relative 10⁻⁹, or
different. With `--check`, it fetches and compares again, and fails if a run's environment or document, or any
verdict, has changed. Differences below 10⁻⁹ are floating-point noise that can vary by machine, so they are recorded
but not checked. The MVP's record is `compose/live/tnf_field_cell.yaml`
({doc}`../design/roadmap`, phase 6).

## Generated, not hand-written

Every case except the two harness cases (copied unchanged from compose-api) is written by a script beside it
(`checks/<group>/make_*.py`), which computes its expected values from the
oracle: the reference file, the corpus or the closed form. Re-running the script regenerates the case exactly.
